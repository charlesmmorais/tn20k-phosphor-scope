# 📚 Theory - How each piece works

[🇧🇷 Versão em português](theory_pt.md) · [⬅️ Back to README](../README.en.md)

This document explains, calmly and from scratch, **why** each block exists and **how** it works. The goal is that a maker who has never touched an FPGA can follow along - and that seasoned folks pick up a trick or two.

---

## 1. The big idea: the FPGA as a digital CRT

An analog oscilloscope has a **cathode-ray tube (CRT)**. Inside it:

- an **electron beam** is deflected by voltages (X horizontal, Y vertical) and traces a path;
- where the beam hits, a **phosphor** layer absorbs energy and **glows**;
- when the beam leaves, the phosphor **cools** and the glow **decays** over a few milliseconds.

We reproduce all three in digital logic:

| Analog world | Our digital equivalent |
|--------------|------------------------|
| Beam deflected by X/Y | `signal_gen` (makes X,Y) + `beam_plotter` (traces the line) |
| Phosphor lighting up | `scope_engine` adds brightness into the `framebuffer` |
| Phosphor cooling down | `scope_engine` sweeps and subtracts brightness (decay) |
| Green phosphor screen | `colorizer` (P31 palette) |
| Tube / glass | the monitor, over HDMI |

The big difference from an ordinary "computer drawing" is the **brightness ∝ speed** item - see section 4.

---

## 2. DDS - generating the points (`signal_gen.v`)

**DDS (Direct Digital Synthesis)** is the simplest, most elegant way to make a periodic wave in hardware.

The idea: a **phase accumulator** (a register you keep adding the same value to) spins like a clock hand. The high bits of that accumulator are the "angle", which we use to index a **sine table**.

```verilog
ph_x <= ph_x + (STEP * rx);     // 16-bit accumulator
addr_x = ph_x[15:8];            // top 8 bits = angle 0..255 (0..360°)
sin_x  = sine_lut[addr_x];      // sine value
```

- The **bigger** the step (`STEP * rx`), the faster the hand spins → **higher frequency**.
- The **table** (`sine_lut.hex`) holds 256 samples of one sine period, amplitude ±120, in 8-bit two's complement. It's generated by Python so that **hardware and simulation use the exact same numbers**.

### Lissajous figures (XY mode)

If we drive X = sin(a·t) horizontally and Y = sin(b·t) vertically, the path closes into a **Lissajous figure**. The ratio **a:b** sets the shape:

- 1:1 → an ellipse (or a line/circle, depending on phase);
- 1:2 → a sideways "8";
- 2:3, 3:4, 3:5 → ever more elaborate knots.

We control the ratio with `rx` and `ry`. A **slow phase offset** (`morph`) gradually shifts X's phase, making the figure **rotate/open** - the "living" look of a real analog scope, where nothing ever stands perfectly still.

### YT mode and triggering

In **YT** mode (time on the X axis), X is a **sweep** (ramps 0→319 and restarts) and Y follows the waveform. There's a classic problem: if the sweep restarts at a random instant, each pass shows the wave at a different phase and the screen becomes a **blurry mesh**.

The fix every real scope uses is **triggering**: always start the sweep at the same point of the wave. We implement it simply - when the sweep restarts, we **also zero the wave phase** (`yt_ph <= 0`). Result: a **stable, sharp** waveform.

## 3. Bresenham - joining the points (`beam_plotter.v`)

`signal_gen` delivers spaced-out points; we need to draw the **line** between one point and the next, pixel by pixel. **Bresenham's algorithm** does it using **only adds, subtracts, and compares** - no multiply or divide, perfect for hardware.

It keeps an "accumulated error" that decides, each step, whether to move in X, Y, or both:

```verilog
e2 = 2*err;
if (e2 > -ady) begin err <= err - ady; cx <= cx + sx; end
if (e2 <  adx) begin err <= err + adx; cy <= cy + sy; end
```

When the jump between two points is too big (above `MAX_SEG`), we treat it as a **retrace** (pen-up) and do **not** draw the line - that's what avoids a streak across the screen when the YT sweep "wraps" from end back to start. In a real CRT, the beam is blanked during retrace too.

### valid/ready handshake

The plotter and the `scope_engine` talk via a **valid/ready handshake**: the plotter presents a pixel and only advances when the engine **accepts** it. This guarantees that **no pixel is ever dropped**, even when the engine is busy decaying the screen. The plotter's outputs are **combinational** (they reflect the current pixel immediately), which avoids a 1-cycle skew that would duplicate or drop pixels - a subtle bug that only shows up when you simulate carefully.

## 4. 🔑 Brightness ∝ speed (the analog heart)

This is the part that makes the result look **truly analog**.

In a CRT, a point's brightness depends on **how much energy** the beam deposited there, which depends on **how long** the beam dwelled there. Where the path is **slow** (the turning points, the returns of a Lissajous), the beam lingers and the phosphor glows **a lot**. Where it's **fast** (the straight middle runs), the glow is **faint**.

How do you measure "speed" in cheap hardware? Trick: the `beam_plotter` already knows each segment's **length** (Bresenham's `max(|dx|,|dy|)`). Since each segment is drawn in the same time interval, **long length = fast beam = little brightness**, and vice-versa:

```verilog
// short segments (slow beam) → high brightness
if      (steps <= 1)  bright = 15;
else if (steps <= 2)  bright = 12;
else if (steps <= 4)  bright = 9;
...
else                  bright = 2;   // long segments (fast beam) → low brightness
```

It's **a six-line lookup** - and that's exactly what separates a figure that looks like a Tektronix from one that looks like a calculator screenshot. Notice the dazzling turning points of the Lissajous in the README: that's Z-axis modulation at work.

## 5. The phosphor: light up and fade (`scope_engine.v` + `framebuffer.v`)

### The framebuffer fits inside the FPGA

We store the screen in a **320×240 pixel, 4-bit (16 brightness levels) each** memory = 307,200 bits. That fits comfortably in the GW2AR-18's **BSRAM** (~828 kbit), so we **don't need external SDRAM**. This massively simplifies the design and makes it 100% simulable. We then scale 2× (320→640, 240→480) at display time.

The memory is **dual-port** (two independent ports):
- **Port A**: the video stage **reads** to display.
- **Port B**: the `scope_engine` does **read-modify-write** (light up and fade).

### Drawing (DRAW) and fading (DECAY) at the same time

The `scope_engine` interleaves two tasks on port B:

- **DRAW**: when the plotter hands a pixel, add brightness there (saturating at 15). That's the phosphor lighting up.
- **DECAY**: continuously, a pointer sweeps the **entire** memory subtracting 1 from each pixel's brightness. That's the phosphor cooling down.

DRAW has **priority**: when there's a new pixel to draw, it goes first; in the spare cycles, the engine keeps fading. Since BSRAM has **1 cycle of read latency**, each operation is a 2-cycle read-modify-write (read → compute → write).

The DECAY rate sets the **phosphor persistence**: fade slowly = long trail (radar style); fade fast = sharp trace with no ghost. Just one parameter.

> On power-up, a **CLEAR** phase zeroes the whole memory before starting - guaranteeing a clean black screen with no power-up garbage.

## 6. Color and graticule (`colorizer.v`)

The 4-bit intensity becomes a **P31 green phosphor** RGB color (the classic scope green). At the highest levels we add a bit of red and blue so the trace **peak** looks "white-hot", like a saturated CRT.

Under the trace we draw the **graticule** - the scope grid, with lines every 64 pixels, stronger center axes, and a border. The trace always beats the grid (we take the greater green), so the figure stays crisp over the grid.

## 7. The clocks (`gowin_rpll.v`)

We need two clocks from the **27 MHz** crystal:

- **25.2 MHz** - the **pixel** clock for 640×480 @ 60 Hz (the VESA standard is 25.175 MHz; 25.2 is close enough).
- **126 MHz** - exactly **5×** the pixel clock, for the TMDS serializer (each pixel becomes 10 bits, sent in 5 cycles at double rate - DDR).

We use the **rPLL** (Gowin's built-in PLL): `27 ÷ 3 × 14 = 126 MHz` (with the internal VCO at 1008 MHz, inside the valid range). Then a **CLKDIV ÷5** derives 25.2 MHz from the same signal, keeping the two clocks **phase-aligned** - essential for the serializer to work.

---

## 8. TMDS / DVI - speaking HDMI's language (`tmds_encoder.v`)

HDMI (in DVI mode) doesn't send "raw" color bits. It uses **TMDS - Transition Minimized Differential Signaling**, an **8b/10b** encoding: each color byte (8 bits) becomes a **10-bit** symbol that does two things:

1. **Minimizes transitions** - by chaining XOR or XNOR we pick the form with the fewest 0↔1 flips, which reduces electromagnetic interference on the cable.
2. **Balances DC** - a "disparity" counter tracks how many 0s and 1s have been sent and, when needed, **inverts** the symbol to keep the count of 0s and 1s balanced over time. The receiver needs this to recover the signal level.

Outside the visible area (during blanking), instead of color we send one of the **4 control tokens**, which carry the **hsync** and **vsync** syncs.

This module is **pure logic** and so is the most rigorously tested: the testbench does a **round-trip** (encode then decode, checking the original byte comes back intact) over thousands of symbols, and verifies the DC disparity stays **bounded** (doesn't grow forever). That's how we caught a real bug: without initializing the disparity counter, DC balance broke.

---

## 9. Serialization and the differential pairs (`hdmi_serializer.v`)

Each color channel is 10 bits per pixel at 25.2 MHz → **252 Mbit/s** per channel. To push that down a single wire pair we use the **OSER10** primitive (a 10:1 DDR serializer running at 126 MHz) and the **ELVDS_OBUF** buffer, which turns the signal into a **differential pair** (two wires with opposite signals) - the way HDMI expects to receive it. The clock channel sends the fixed pattern `1111100000`.

> These are **Gowin-specific** primitives: in simulation they are replaced by simple models (`\`ifdef SIM`), which lets us simulate the whole top without the vendor libraries. The generic logic (timing, framebuffer, DDS, TMDS) is all simulable and tested.

---

## 10. The video pipeline and alignment

There's an important subtlety: BSRAM has **1 cycle of read latency**. So when `video_timing` produces position (x,y), the pixel value only comes out of the framebuffer **one cycle later**. If we don't handle this, the color would come out "shifted" and the syncs wouldn't line up with the image.

The fix is to **delay** the position and syncs by 1 cycle (`_d1` registers) to match exactly the data leaving memory. Pipeline alignment is the kind of detail that never shows up in a pretty diagram, but it's the difference between a perfect image and a "shaky" one - and exactly the kind of thing simulation helps you nail before programming the FPGA.
